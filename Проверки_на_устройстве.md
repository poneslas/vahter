# Проверки на устройстве: пробник

Обновлено 17.10.2026. Требования к одноразовому диагностическому приложению. Оно за один прогон на Samsung Galaxy S24 Ultra (One UI 9, Android 17) проверяет скользкие места платформы, на которых держится дизайн (`Архитектура.md`, разделы 3, 3.1, 3.2, 4, 9.6.1, 18.4; `Продукт.md`, 5.1, 5.2, 5.7, 5.17), и собирает диагностику. Вопрос один: **заработает ли это вообще и как быстро**. Продукта здесь нет.

Пометки в тексте:
- **[док]** — написано в документации Android, ссылка в разделе 8;
- **[AOSP]** — прочитано в исходниках AOSP (`main`, 17.10.2026); Samsung мог поменять;
- **[?]** — не подтверждено, проверит тест.

## 1. Границы

- Пробник — не прототип Таси: ни мозга, ни ленты, ни дизайна. Серые экраны, кнопки, таймеры, лог.
- Свой `applicationId` — **`ru.poneslas.tasya.probe`**, чтобы не трогать данные и роль будущего `ru.poneslas.tasya`. Подпись — отладочный ключ.
- `minSdk 34`, `targetSdk 37`: ограничения Android 14–17 должны действовать в полную силу.
- Результат каждой проверки — «прошло / не прошло / частично» и цифры. Решение «основной путь или запасной» принимается по таблице раздела 7 и вписывается в `Архитектура.md`, 18.4.

### 2.4. Сборка и установка

```sh
# Mac: сборка, установка с разрешениями (кроме локальной сети), роль, adb reverse
probe/scripts/install.sh --run
python3 probe/scripts/serve.py &      # тестовый сервер для П9, П14, П15, П23

# роль помощника без настроек (для серий; П1 проверяет и путь через настройки)
adb shell cmd role add-role-holder android.app.role.ASSISTANT ru.poneslas.tasya.probe
adb shell cmd role get-role-holders android.app.role.ASSISTANT

# открыть лист без кнопки — как удержание помощника
adb shell input keyevent KEYCODE_ASSIST
```

`adb shell cmd voiceinteraction show` **не работает** без root: `SecurityException: requires ACCESS_VOICE_INTERACTION_SERVICE` (проверено на эмуляторе Android 17, 17.10). Поэтому серии без человека пробник гоняет сам: он и есть активный помощник, ему `showSession`/`hide` разрешены.

Перед прогоном: Auto Blocker выключен (иначе `adb` по USB не работает), «Отладка по USB» включена, боковая кнопка → «Цифровой помощник», батарея пробника и ntfy — «Без ограничений».

### 2.6. Как меряем время

| Отрезок | Как | Точность |
|---|---|---|
| Внутри приложения | `SystemClock.uptimeMillis()` в колбэках: `VoiceInteractionService.onPrepareToShowSession` (самая ранняя точка в нашем коде, API 33 [AOSP]) → `onCreate` сессии → `onCreateContentView` → `onShow` → первый кадр (`ViewTreeObserver.OnDrawListener` / `Choreographer`) | ±1 кадр |
| Нажатие → лист из args | система кладёт в `args` сессии `android.intent.extra.TIME` и `invocation_time_ms` — время вызова; на эмуляторе это шкала `uptimeMillis` (на телефоне сверить [?]). Пробник считает «нажатие → кадр» сам | ±1 кадр, если часы угаданы |
| Нажатие → лист (настоящая кнопка) | `scripts/trace.sh`: Perfetto с `android.input.inputevent` и `android.surfaceflinger.frametimeline`; в трассе видно нажатие и первый кадр нашего окна | ±1 кадр |
| Серии без человека | пробник сам: `showSession` → первый кадр → `hide`, 20 раз; или `scripts/series.sh`: `input keyevent KEYCODE_ASSIST` → маркер `FRAME` в logcat | ±1 кадр |
| Глазами | запись экрана 120 fps вторым телефоном — только если Perfetto ничего не покажет | ±8 мс |

Холодный и тёплый старт меряем отдельно: холодный — после `adb shell am force-stop` (роль при этом не теряется [?]; если система не поднимет VIS сама — отметить).

## 4. Вызов и окно

### П1. Роль помощника

**Зачем.** Без роли нет ни кнопки, ни листа. Роль не запрашивается диалогом (`requestable="false"`) и сбрасывается при обновлении, если у сервиса нет `RecognitionService` [AOSP: `VoiceInteractionManagerService.resetServicesIfNoRecognitionService`]. `Архитектура.md`, 3; С10.

**Шаги.**
1. Пробник: `RoleManager.isRoleAvailable(ROLE_ASSISTANT)`, `isRoleHeld`. Человек: «Открыть настройки» → `Settings.ACTION_VOICE_INPUT_SETTINGS`; если не открылось — `ACTION_MANAGE_DEFAULT_APPS_SETTINGS`. Выбирает пробник.
2. Пробник в `onResume` фиксирует, что роль у него, и сколько экранов прошёл человек (заметка).
3. Человек на Mac: `scripts/bump.sh` → `adb install -r` сборки `versionCode+1`. Пробник по `ACTION_MY_PACKAGE_REPLACED` пишет `isRoleHeld` и `VoiceInteractionService.isActiveService`.
4. Повтор шага 3 на **сборке без `recognitionService`** в XML (флаг сборки `-PnoRecognizer`): ожидаем, что роль слетит. Это контрольный опыт: доказывает, что дело именно в нём.
5. После обратной установки нормальной сборки — вернуть роль через `cmd role`.

**Прошло.** Роль ставится через настройки; переживает два обновления подряд с `RecognitionService`; без него — слетает (иначе наш вывод о причине неверен).

**Диагностика.** Какие интенты настроек открылись (`resolveActivity`, имя активности Samsung); держатель роли до и после каждого шага; `Settings.Secure.voice_interaction_service` и `assistant` (через `adb shell settings get secure …`); logcat `VoiceInteractionManager` при установке.

**Если нет.** Плашка «Вернуть» после каждого обновления (уже в дизайне); входы, не зависящие от роли: плитка и ярлыки работают только при роли (П11), значит — обычная активность-лист как крайний запасной.

### П2. Боковая кнопка и время до листа

**Зачем.** Главный вход. One UI позволяет назначить на удержание «Цифровой помощник» вместо Bixby. Цель — лист ≤ 300 мс (С1), из него видоискатель ≤ 700 мс (С13). С5.

**Шаги.**
1. Человек: «Дополнительные функции → Боковая кнопка → Нажатие и удержание → Цифровой помощник». Пробник показывает этот путь текстом, проверить настройку программно не может [?].
2. `scripts/trace.sh` запускает Perfetto на 60 с. Человек 10 раз удерживает кнопку и закрывает лист свайпом, между нажатиями ~3 с. Пять — при заблокированном экране (это же П5).
3. Пять нажатий после `am force-stop` (холодный процесс).
4. Те же 20 открытий без человека: пробник сам через `showSession` — для сравнения, сколько стоит сама кнопка.

**Прошло.** Каждое удержание открывает наш лист, не Bixby и не Gemini; медиана «нажатие → первый кадр листа» ≤ 300 мс тёплым, ≤ 700 мс холодным; 90-й процентиль записан.

**Диагностика.** Флаги `onShow` (ожидаем `SHOW_SOURCE_PUSH_TO_TALK` или `SHOW_SOURCE_ASSIST_GESTURE` — какой ставит Samsung, неизвестно [?]); `args` из `onShow` (есть ли что-то от Samsung); тайминги по точкам из 2.6; был ли процесс жив (`Application.onCreate` в этом открытии или нет); пропущенные кадры анимации появления.

**Если нет.** Кнопка не вызывает наш лист → плитка, ярлык, виджет (`Архитектура.md`, 3). Медленно → П3 покажет, где время: создание процесса, Compose, первый кадр.

### П3. Окно сессии: Compose, кадры, клавиатура

**Зачем.** Лист — `ComposeView` в окне `TYPE_VOICE_INTERACTION`; сессия сама реализует `LifecycleOwner`, `SavedStateRegistryOwner`, `ViewModelStoreOwner`. Клавиатура в окне работает, если окно берёт фокус (`takesFocus=true` у окна сессии) [AOSP]. Частичный лист требует своего `onComputeInsets`. С1; `Архитектура.md`, 3.

**Шаги (пробник сам).**
1. 20 открытий `series.sh`; лист с анимацией появления по `Архитектура.md`, А.6 и простым списком из 50 строк.
2. Скролл списка 5 с программно (`performScroll`), подсчёт кадров через `JankStats` / `FrameMetrics` окна.
3. Фокус в поле → `WindowInsetsCompat.isVisible(ime())`, высота IME, видна ли строка ввода над клавиатурой (`imePadding()` + `SOFT_INPUT_ADJUST_RESIZE`).
4. Человек: набрать текст, повернуть телефон, проверить, что клавиатура вернулась (на Android 17 после поворота её, по нашим данным, надо запрашивать явно — проверить); голосовой ввод Samsung-клавиатуры работает при нашем микрофоне?
5. Нажатие по затемнению вне листа: `onComputeInsets` с `TOUCHABLE_INSETS_REGION` — касание уходит в приложение под листом или перехватывается (нам нужно «перехватывается»).

**Прошло.** Открытие ≤ 300 мс медиана; ≥ 95 % кадров в бюджете 8,3 мс (120 Гц) или 16,6 мс; клавиатура открывается, поле не уходит под неё, после поворота клавиатура возвращается.

**Диагностика.** `window.attributes` (type, flags, softInputMode), `Display.refreshRate`, insets IME и навигации, время первой композиции, исключения `ViewTreeLifecycleOwner not found`, утечки `ViewModelStore` после 20 открытий (размер кучи до/после).

**Если нет.** Лист на View, Compose — в остальных экранах (`Архитектура.md`, 16). Клавиатура не работает → ручной ввод разворачивает лист в приложение (П10).

### П4. Микрофон в окне сессии и процесс после скрытия

**Зачем.** Запись без foreground-сервиса, пока лист показан. По исходникам: окно сессии привязано с `BIND_TREAT_LIKE_ACTIVITY | BIND_TREAT_LIKE_VISIBLE_FOREGROUND_SERVICE`, а сам VIS — с `BIND_FOREGROUND_SERVICE | BIND_INCLUDE_CAPABILITIES` [AOSP]. Отсюда два следствия, которые и проверяем: запись идёт, и процесс после скрытия **не** становится фоновым. `Архитектура.md`, 3.

**Шаги (пробник сам).**
1. Пробник открывает лист (`showSession`) → `AudioRecord` 16 кГц моно, 5 с → RMS, доля нулевых сэмплов → `hide`.
2. Сразу после `hide` — попытка записи из `Conversation` (без окна): ожидаем тишину или ошибку; фиксируем, что именно.
3. Каждые 10 с в течение 5 минут после `hide`: `ActivityManager.getMyMemoryState().importance`, жив ли процесс.
4. Человек (по желанию): говорит в шаге 1, слышит запись воспроизведением.

**Прошло.** Шаг 1 — ненулевой сигнал уже в первых 300 мс записи (на эмуляторе 17.10 при открытом листе было 94–98 % нулевых сэмплов, после закрытия — нормальный сигнал; причина не найдена — на S24 проверить первым делом), `startRecording` без исключений, время от `onShow` до первого буфера ≤ 100 мс. Шаг 3 — важность и жизнь процесса записаны (это вход в П9).

**Диагностика.** `AudioRecord.state`, `recordingState`, `AudioManager.getActiveRecordingConfigurations()` (заглушен ли клиент `isClientSilenced`), индикатор микрофона Android, важность процесса по времени.

**Если нет.** Запись через короткий FGS типа `microphone`, запущенный из видимого листа — исключение «приложение предоставляет `VoiceInteractionService`» для while-in-use есть в документации [док].

### П5. Поверх экрана блокировки

**Зачем.** Вопросы с блокировки — штатный сценарий (`Продукт.md`, 5.7). Окно сессии показывается поверх блокировки; если блокировка включилась при открытом листе, по умолчанию `onLockscreenShown()` вызывает `hide()` [AOSP]. Разблокировка — через свою активность: `startAssistantActivity` → `setShowWhenLocked(true)` → `KeyguardManager.requestDismissKeyguard` [док].

**Шаги (человек).**
1. Заблокировать, удержать боковую кнопку: лист виден? (тайминг из П2).
2. Нажать «Микрофон», сказать фразу → запись идёт (повтор П4.1 на блокировке).
3. Нажать «Разблокировать и выполнить» → `UnlockActivity` → ввод отпечатка/PIN → `onDismissSucceeded` пишет время, лист снова показан (`showSession` из сервиса) или нет.

5. Двойное нажатие боковой кнопки при блокировке (камера Samsung) — не путается ли с нашим удержанием.

**Прошло.** 1–3 работают; после разблокировки отложенное действие выполнено, понятно, вернулся ли лист сам.

**Диагностика.** `KeyguardManager.isKeyguardLocked`, `isDeviceSecure`; флаги окна сессии; колбэки `requestDismissKeyguard` с временем; что видно поверх: наш лист или лист под шторкой блокировки (скриншот через `adb exec-out screencap` — на блокировке может быть закрыт [?]).

**Если нет.** На блокировке лист сразу просит разблокировку (хуже по секундам, но честно). Если лист не показывается вообще — `onLaunchVoiceAssistFromKeyguard` + активность с `FLAG_SHOW_WHEN_LOCKED` [AOSP: так требует сам метод].

### П8. Файл и фото из галереи из листа

**Зачем.** «Скрепка» в поле ввода. У сессии нет `startActivityForResult`, результат можно получить только через свою активность. Задачи, запущенные из активности помощника, идут в обычный слой, а не в слой помощника [док: `startAssistantActivity`] — галерея может уйти **под** лист [?]. Права на URI из результата живут до перезапуска телефона или остановки приложения; для `OPEN_DOCUMENT` можно `takePersistableUriPermission` [док]. Встроенный Photo Picker (`androidx.photopicker`, `EmbeddedPhotoPicker` на `SurfaceView`) работает на Android 14 с SDK Extensions ≥ 15 [док] — мог бы жить прямо в листе, но пример в документации — в активности [?].

**Варианты.**

| Вариант | Как |
|---|---|
| 8.1 Батут + Photo Picker | `startAssistantActivity(PickerTrampolineActivity)` → `PickVisualMedia` / `PickMultipleVisualMedia` → URI → копия в `cacheDir/attachments` сразу → `finish()` |
| 8.2 Батут + `ACTION_OPEN_DOCUMENT` | то же, `OpenDocument(arrayOf("*/*"))`, файл до 50 МБ |
| 8.3 Встроенный пикер в листе | `EmbeddedPhotoPicker` в `ComposeView` окна сессии |
| 8.4 «Поделиться в Тасю» | `ACTION_SEND` из галереи Samsung → `ShareActivity` → `showSession` с вложением |

**Шаги.** Человек по очереди: открыть лист → нажать «Фото» / «Файл» → выбрать → вернуться. Пробник после каждого: где был лист (`onHide` вызван или нет, когда), куда вернулся пользователь, пришёл ли результат, удалось ли прочитать и скопировать файл до `finish()`, время «нажал → пикер виден» и «выбрал → миниатюра в листе». То же с блокировки (ожидаем просьбу разблокировать). 8.4 — из «Галереи».

**Прошло.** Хотя бы один из 8.1–8.3 для фото и 8.2 для файла: результат доходит, лист после выбора снова виден (сам или через `showSession`), без промежуточного рабочего стола.

**Диагностика.** `SdkExtensions.getExtensionVersion(34)`, `isPhotoPickerAvailable`, пакет активности пикера; порядок `onHide`/`onShow` сессии с временем; код результата, MIME, размер, время копирования; `SecurityException` при чтении URI после `finish()` батута (специально пробуем читать через 5 с).

**Если нет.** Скрепка разворачивает лист в приложение (П10) и выбирает файл там; после выбора — «Свернуть». На одно движение больше, но надёжно.

### П9. Загрузка вложения, если лист закрыли

**Зачем.** Фото ушло в загрузку, человек смахнул лист. `Архитектура.md`, 3: закрытие листа не должно терять отправленное. По `Продукт.md`, 5.17 байты грузятся на сервер сразу после снимка, а мозгу вложение уходит позже — не раньше 2 с и, если в поле начат вопрос или идёт запись, вместе с ним. Пробник проверяет только первую часть — доживает ли **загрузка байтов**; склейку с вопросом — нет, это логика приложения, а не платформы. Варианты по документации: обычная задача `WorkManager` (с ускорением `setExpedited`); **задача пользовательской передачи данных** (UIDT, Android 14+, `RUN_USER_INITIATED_JOBS`, ставится только пока приложение видно пользователю или может запускать активности из фона, нужна сетевая цель и уведомление; Jetpack её не поддерживает) [док]; FGS `dataSync` — запуск из фона запрещён с Android 12 кроме исключений, у `dataSync` на Android 15+ лимит 6 часов в сутки [док]. Ключевой вопрос: считается ли показанный лист «видимым приложением» для UIDT и FGS [?]. По П4 процесс помощника, вероятно, живёт и после закрытия листа — тогда обычной корутины может хватить [?].

**Шаги.**
1. Тестовый сервер: `python3 -m http.server`-подобный приёмник на Mac или `https://<сервер>/tasya/` — PUT 20 МБ, скорость искусственно 2 Мбит/с.
2. Для каждого варианта (корутина в процессе, `WorkManager` expedited, UIDT, FGS `dataSync`): открыть лист → «Загрузить» → через 2 с `hide()` → ждать.
3. Повтор с экраном, выключенным сразу после скрытия, и с `adb shell am kill` (не `force-stop`) посреди загрузки — что из вариантов догружает.

**Прошло.** Хотя бы один вариант догружает 20 МБ после закрытия листа и при выключенном экране; запуск варианта из показанного листа не бросает исключение.

**Диагностика.** Для каждого: исключение при запуске (`ForegroundServiceStartNotAllowedException`, ошибка `JobScheduler.schedule`), время до старта, итог (`onStopJob`, причина остановки `JobParameters.getStopReason`), байты переданы, важность процесса по времени, уведомление показано или нет.

**Если нет.** Загрузка до закрытия листа с пометкой «Не закрывайте, пока грузится» — плохо; или вложение догружается при следующем открытии листа из очереди (как реплики без сети, `Архитектура.md`, 9.3). Если лист закрыли, пока вложение «ждёт ваш вопрос», — оно уходит без вопроса после догрузки (решение продукта, не платформы).

### П10. Развернуть лист в приложение и обратно

**Зачем.** «Развернуть» = `startAssistantActivity(MainActivity)` → лист скрывается, когда активность нарисовала первый кадр; «Свернуть» = `finish()` + `showSession`. Цель — без мигания и без рабочего стола между кадрами. С12; `Архитектура.md`, 3.1.

**Шаги.**
1. Пробник 20 раз: лист → «Развернуть» (анимация до полного экрана → `startAssistantActivity(FullActivity, makeCustomAnimation(0,0))` → по первому кадру `FullActivity` — `hide()` сессии) → 1 с → «Свернуть» (`showSession` из сервиса, затем `finish()`; и в обратном порядке — сравнить).
2. Запись экрана `adb shell screenrecord` на всё время + Perfetto. Человек смотрит запись покадрово, ставит отметку «мигание: да/нет».
3. Проверки: `FullActivity` в «Недавних» есть? «Назад» в ней — куда? Home из неё и из листа. Повтор над приложением с белым и тёмным фоном.
4. Вариант `setUiEnabled(false)` + только активность (как у Gemini?) — для сравнения [?].

**Прошло.** 20 из 20 без кадра рабочего стола или пустого окна; время «нажал → полный экран активности» ≤ 250 мс; «Свернуть» возвращает лист над тем же приложением.

**Диагностика.** Код возврата `startAssistantActivity` (на скрытой сессии — `START_ASSISTANT_HIDDEN_SESSION` [AOSP]); время первого кадра активности; порядок `onHide`/`onDestroy` сессии; `windowingMode`/`activityType` задачи (`adb shell dumpsys activity activities`), пропущенные кадры.

**Если нет.** Растворение 120 мс на передаче (`Архитектура.md`, 3.1); при постоянном мигании — «Развернуть» открывает приложение обычным `startActivity`, без иллюзии одного листа.

## 6. Входы, уведомления, сеть, обновление, голос

### П11. Ярлыки иконки и плитка быстрых настроек

**Зачем.** Ярлыки открывают свой режим (`Продукт.md`, 5.17), плитка — запасной вход (`Архитектура.md`, 3). `showSession` есть только у `VoiceInteractionService`; система проверяет, что вызывающий — UID текущего помощника, без проверки «на переднем плане» [AOSP: `enforceIsCurrentVoiceInteractionService`, `showSessionLocked`]. Значит, любой компонент в нашем процессе может вызвать его через ссылку на живой сервис (`ServiceHolder`, заполняется в `onReady`). Второй путь — `Activity.showAssist(Bundle)`: работает, только если активность на переднем плане, и сессия получает `SHOW_SOURCE_APPLICATION` [AOSP]. Есть ли у Samsung свои ограничения — [?].

**Варианты.**

| Вход | Как |
|---|---|
| 11.1 Ярлык → батут → сервис | статический ярлык (`shortcuts.xml`) → прозрачная `ShortcutTrampolineActivity` с `mode=…` → `ServiceHolder.service.showSession(bundleOf("mode" to …), 0)` → `finish()` без анимации |
| 11.2 Ярлык → батут → `showAssist` | то же, но `showAssist(bundle)` |
| 11.3 Плитка → сервис | `TileService.onClick` → `ServiceHolder.service.showSession(...)`; шторку закрыть нечем, кроме запуска активности, поэтому сессия в `onShow` вызывает `closeSystemDialogs()` (закрывает шторку, блокировку не снимает [AOSP]); переопределить `onCloseSystemDialogs`, чтобы лист не закрыл сам себя |
| 11.4 Плитка → активность | `startActivityAndCollapse(PendingIntent)` (вариант с `Intent` на Android 14+ бросает исключение [AOSP]) → батут из 11.1 |
| 11.5 Ярлык камеры | 11.1 + П6.1/П6.2: ярлык «Гастрогид» сразу в видоискатель |

**Шаги.** Человек: по 5 раз каждый вход, с разблокированного экрана; плитку — и с заблокированного (`TileService.isLocked`, `unlockAndRun`). Если `ServiceHolder` пуст (процесс только что поднят ярлыком, VIS ещё не привязан) — пробник ждёт `onReady` до 1 с и пишет, сколько ждал.

**Прошло.** Лист открывается в нужном режиме (`args` дошли до `onShow`), ≤ 400 мс от касания, без мелькания батута и без открытой шторки.

**Диагностика.** Флаги и `args` в `onShow`; `showAssist` вернул `true/false`; `SecurityException`; было ли `ServiceHolder` пустым; время касание → `onClick`/`onCreate` батута → `onShow` → кадр; осталась ли шторка (`closeSystemDialogs` подействовал?).

**Если нет.** Ярлыки открывают `MainActivity` в нужном режиме (полный экран, не лист); плитка — так же.

### П12. Пуш-уведомление открывает лист

> **План 17.10:** в v1 мозг — DeepSeek по API, пуш-сервера нет; ответ после закрытия листа показывает сам телефон (П9). П12 нужна к v2 (Hermes).

**Зачем.** Ответ пришёл при закрытом листе — уведомление, нажатие открывает лист с разговором (`Архитектура.md`, 9.5). Доставка — UnifiedPush через свой ntfy. Нажатие на уведомление не может запустить активность через приёмник или сервис-батут с Android 12 [док: notification trampolines]; но `showSession` — не запуск активности, поэтому `PendingIntent.getBroadcast` → приёмник → `showSession` формально не запрещён [AOSP; на Samsung — ?].

**Шаги.**
1. Человек: поставлен ntfy (дистрибьютор), пробник регистрируется через коннектор UnifiedPush, показывает endpoint; «Скопировать curl».
2. С Mac: `curl -d '{"seq":1}' <endpoint>` — пробник ловит, пишет задержку (время отправки в теле).
3. Пробник показывает три уведомления: (а) `getActivity` → `NotifyTrampolineActivity` → сервис; (б) `getBroadcast` → `NotifyReceiver` → сервис; (в) батут → `showAssist`. Человек нажимает каждое по 3 раза, в том числе с блокировки.
4. Сон: телефон заблокирован 30 мин, потом `curl` — пришло ли и за сколько (полноценный С9 на 3 дня — вне пробника).

**Прошло.** Пуш доходит ≤ 5 с при включённом экране и после 30 минут сна; хотя бы один вариант открывает лист с правильными `args` за ≤ 500 мс, шторка закрыта.

**Диагностика.** Задержка доставки, `SHOW_SOURCE_NOTIFICATION` в флагах (ставит ли его система при нашем вызове — вряд ли, флаги задаём сами [?]), исключения, осталась ли шторка, `isIgnoringBatteryOptimizations` пробника и ntfy, `PowerManager.isDeviceIdleMode` в момент приёма.

**Если нет.** Нажатие открывает `MainActivity` с разговором (полный экран). Пуш не доходит — исключение из оптимизации батареи, копия в Telegram (`Архитектура.md`, 16).

### П13. Сервер в локальной сети, Auto Blocker

> **План 17.10:** v1 ходит только в интернет (api.deepseek.com); локальная сеть нужна к v2, если Hermes будет в домашней сети.

**Зачем.** При `targetSdk 37` доступ в локальную сеть закрыт по умолчанию; нужно runtime-разрешение `ACCESS_LOCAL_NETWORK` из группы «Устройства поблизости»; при запрете TCP обычно падает по таймауту, UDP — `EPERM`; DNS на порт 53 разрешён [док]. Через домен и Tailscale разрешение не нужно (`Архитектура.md`, 18.4). Что считается «локальной сетью» для адресов Tailscale `100.64.0.0/10` — [?].

**Шаги (пробник сам, человек жмёт «Разрешить»).**
1. Без разрешения: TCP-подключение к `192.168.x.x:8080` (Mac в той же Wi-Fi, `python3 -m http.server 8080`), к `<домен>:443`, к адресу Tailscale (если стоит) — время и ошибка каждого.
2. Запрос разрешения → повтор шага 1. Отдельно — то же **из окна листа** (сессия), не из активности.
3. Auto Blocker: пробник не видит его состояние [?]; человек ставит галочку в шапке. Проверка косвенная: при включённом Auto Blocker `adb install` должен падать — один раз включить и попробовать, записать текст ошибки.

**Прошло.** Без разрешения LAN не работает, с разрешением работает; домен работает всегда; понятно, нужен ли запрос для Tailscale.

**Диагностика.** Тип ошибки и время до неё, `LinkProperties` (адреса, DNS), `NetworkCapabilities`, статус разрешения, ответ `getaddrinfo` для `.local`.

**Если нет.** Только домен с TLS или Tailscale; LAN-адрес в настройках не предлагаем.

### П14. Самообновление без окна и роль после него

**Зачем.** `PackageInstaller` с `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` ставит обновление без подтверждения, если есть `UPDATE_PACKAGES_WITHOUT_USER_ACTION`, приложение обновляет само себя и `targetSdk` свежий [док]; иначе — `STATUS_PENDING_USER_ACTION` с системным окном. После обновления роль должна остаться (П1). `Архитектура.md`, 3.2; С10.

**Шаги.**
1. Первая установка — `adb install` (как бета в жизни). Человек один раз даёт «Установка неизвестных приложений».
2. `scripts/bump.sh` кладёт сборку `versionCode+1` на Mac-сервер; пробник качает, проверяет `sha256`, ставит сессией `PackageInstaller`.
3. Повтор шага 2 с ещё одной сборкой (вторая подряд — как в С10).
4. Повтор, когда первая установка была не через `adb`, а через сам пробник (установщик записи — пробник).
5. Повтор с открытым листом: что происходит с сессией при замене пакета.

**Прошло.** Установка без окна (`STATUS_SUCCESS` без `PENDING_USER_ACTION`) в шагах 2–4; после каждой — `isRoleHeld == true`, боковая кнопка открывает лист новой версии.

**Диагностика.** Все статусы `EXTRA_STATUS`, `EXTRA_STATUS_MESSAGE`, `getInstallSourceInfo` (installer, initiating), время скачивания и установки, роль до/после, `MY_PACKAGE_REPLACED` пришёл через сколько, Auto Blocker.

**Если нет.** Системное окно на каждое обновление (одно нажатие) — приемлемо; роль слетает → плашка «Вернуть».

### П15. Локальное распознавание

**Зачем.** Голос держится на sherpa-onnx (AAR, `arm64-v8a`) + GigaAM v3 e2e_ctc int8 (225 МБ) для чистовика и стриминговом zipformer (24 МБ) для черновика. Цели: чистовик ≤ 0,5 с на 5 с речи, черновик не отстаёт от речи, первые слова через 0,6–0,8 с (`Продукт.md`, 5.3; `Архитектура.md`, 4, 15). С3.

**Шаги.**
1. Загрузка: модели с нашего сервера или с Mac по LAN/`adb push` в `filesDir/models` — время, докачка по `Range` после обрыва (пробник рвёт соединение на 50 %), `sha256`.
2. Холодный старт: процесс после `force-stop` → создание `OfflineRecognizer` GigaAM (время, пик памяти), `OnlineRecognizer` zipformer, Silero VAD. Тёплый — второй раз.
3. Набор WAV в `assets/` (5 фраз по 2, 5, 10, 20 с, записанные тем же S24): RTF чистовика, задержка «конец фразы → текст» на 1, 2, 4 потоках.
4. Стриминг: WAV подаётся кусками по 100 мс с темпом реального времени — задержка появления каждого слова, отставание в конце.
5. 10 минут подряд (WAV по кругу): температура (`PowerManager.getCurrentThermalStatus`, `getThermalHeadroom`), троттлинг по росту RTF, расход батареи.
6. Человек: 5 живых фраз в листе (П4) — субъективное качество черновика, заметка.

**Прошло.** Холодная загрузка GigaAM ≤ 2 с [цель наша, не из документации]; чистовик ≤ 0,5 с на 5 с речи; черновик отстаёт ≤ 0,5 с; за 10 минут без троттлинга выше `THERMAL_STATUS_MODERATE`.

**Диагностика.** Версия sherpa-onnx, `num_threads`, провайдер (CPU), размер и `sha256` моделей, время загрузки каждой, RSS памяти, RTF по каждой WAV, WER против эталонного текста, тепловой статус по минутам, исключения JNI.

**Если нет.** Реже черновики; черновик перезапуском GigaAM по окну 4–6 с; распознавание на сервере (`Архитектура.md`, 4, 16).

### П25. Keystore

**Зачем.** Ключ API DeepSeek хранится зашифрованным AES-ключом из Android Keystore и должен расшифровываться на **заблокированном** телефоне: лист работает поверх блокировки и шлёт запрос. Для Hermes (этап 5) — подпись вызова сервера ключом EC P-256, тоже на блокировке; StrongBox желателен. Ключи должны пережить самообновление.

**Шаги.** П25 (сама): AES-GCM без `setUserAuthenticationRequired` и без `setUnlockedDeviceRequired` (как в продукте) и для сравнения — с `setUnlockedDeviceRequired(true)`; шифртекст тестовой строки сохраняется; EC P-256 без StrongBox и с ним (`StrongBoxUnavailableException` — тоже результат), уровень защиты по `KeyInfo`, 20 подписей — время. После `scripts/bump.sh N` — снова П25: ключи прежней версии расшифровывают прежний шифртекст. П25ч (человек): лист поверх блокировки — расшифровка и подпись в этот момент; после перезагрузки до первой разблокировки — открывается ли лист вообще (приложение не direct-boot-aware [?]).

**Прошло.** На блокировке ключ API расшифровывается, подпись делается; ключ с `unlockedDeviceRequired` — нет (подтверждает, что флаг ставить нельзя); после обновления всё работает.

**Если нет.** Ключ API хранится открытым в данных приложения (защищён песочницей и шифрованием хранилища) — хуже, но работает на блокировке.

**Дополнения к прежним:** П11 — динамические ярлыки своих режимов и закрепление на рабочем столе; П14 — установка при включённом Auto Blocker (статус и текст ошибки); П16 — экраны Bluetooth и Wi-Fi; П12.3 (нажатие на уведомление) нужна уже в v1 и входит в П23.
